# Porting `gen/` to Rust

`gen/` holds code generated from the contracts in `proto/skein/v1/`:

| Directory | What | Generated by |
|---|---|---|
| `gen/go/skein/v1/` | Go messages (`*.pb.go`), gRPC stubs (`*_grpc.pb.go`), grpc-gateway REST handlers (`*.pb.gw.go`) | `buf generate` with the local plugins pinned in `buf.gen.yaml` |
| `gen/go/contracttest/` | tests that the REST mapping, the OpenAPI document and `docs/api/` agree | hand-written; stays in Go |
| `gen/openapi/skein.swagger.json` | the OpenAPI document the gateway serves | `protoc-gen-openapiv2` |
| `gen/python/skein_proto/` | Python messages, stubs and a `descriptor_set.binpb` with comments (the agent builds tool descriptions from it) | `scripts/gen-python.sh` (grpcio-tools) |

`make proto` regenerates all of it and `make proto-stale` fails CI when the
committed output is stale. Nothing here is ported by hand. The Rust port adds
one generated crate, `skein-proto`, from the same `.proto` files, and keeps
the Go, Python and OpenAPI outputs unchanged (the Python services and the
contract tests still use them).

## What the contracts contain

| File | Service | Notes |
|---|---|---|
| `common.proto` | | `PageRequest`, `PageResponse`, `BlockRef` |
| `identity.proto` | `IdentityService` | 18 RPCs; `Authorize`, `ListReadableNotes`, `IssueDelegatedToken`, `RegisterNote` are internal (no REST route) |
| `documents.proto` | `DocumentService` | 14 RPCs; `Sync` is bidirectional streaming (served as a WebSocket) |
| `search.proto` | `SearchService`, `GraphService` | 2 and 6 RPCs |
| `notifications.proto` | `NotificationService` | 5 RPCs; `Subscribe` is server streaming |
| `ml.proto` | `MLService` | 4 RPCs |
| `agent.proto` | `AgentService` | 6 RPCs; `SendMessage` is server streaming |
| `events.proto` | | the `Event` envelope with a `oneof payload`, and every event message |
| `api.proto` | | no messages: the OpenAPI document header (title, version, security) |

They import `google/api/annotations.proto` and `http.proto` (REST routes)
and the `protoc-gen-openapiv2` options, vendored under `proto/third_party/`
so generation works offline.

## Learn first

| Topic | Read | What to take from it |
|---|---|---|
| proto3 | [Language guide (proto3)](https://protobuf.dev/programming-guides/proto3/) | field presence, `oneof`, enums with a zero value, why field numbers never change |
| proto3 JSON | [ProtoJSON format](https://protobuf.dev/programming-guides/json/) | lowerCamelCase names, 64-bit integers as strings, enums by name, `Timestamp` as RFC 3339, defaults omitted; the gateway speaks exactly this |
| buf | [buf generate overview](https://buf.build/docs/generate/overview/), [remote plugins](https://buf.build/docs/bsr/remote-plugins/overview/) | `buf.gen.yaml` v2 with `local:` plugins (what this repo uses) versus `remote:` plugins |
| prost | [prost](https://docs.rs/prost/latest/prost/) | how messages, `oneof` (a Rust enum in a submodule) and enums (an `i32` field plus a Rust enum) are generated |
| tonic codegen | [tonic-prost-build](https://docs.rs/tonic-prost-build/latest/tonic_prost_build/) (tonic 0.14 and later; older releases used [tonic-build](https://docs.rs/tonic-build/latest/tonic_build/)) | `compile_fds` from a descriptor set, `include_file`, `extern_path`, server and client generation |
| buf plugins for Rust | [neoeinstein/protoc-gen-prost](https://github.com/neoeinstein/protoc-gen-prost), [protoc-gen-tonic](https://docs.rs/protoc-gen-tonic), [protoc-gen-prost-crate](https://docs.rs/protoc-gen-prost-crate), [protoc-gen-prost-serde](https://docs.rs/protoc-gen-prost-serde) | the prost, tonic, include-file and pbjson plugins as protoc plugins, so `buf generate` can produce Rust like it produces Go |
| JSON for prost | [pbjson](https://docs.rs/pbjson/latest/pbjson/), [pbjson-build](https://docs.rs/pbjson-build/latest/pbjson_build/), [pbjson-types](https://docs.rs/pbjson-types/latest/pbjson_types/) | serde impls that follow the ProtoJSON mapping (prost's own serde derive does not) |
| descriptors at run time | [prost-reflect](https://docs.rs/prost-reflect/latest/prost_reflect/) | reading `google.api.http` options from the descriptor set, which the Rust gateway needs to build its route table |
| tonic tutorial | [Getting started with gRPC-Rust: streaming](https://codelabs.developers.google.com/grpc/getting-started-grpc-rust-streaming) | a full server and client with all four call types |

## Two ways to generate

### A. `buf generate` into a committed crate (recommended)

This mirrors what the repository does for Go: generated code is committed,
reproducible from pinned plugin versions, and CI fails when it is stale.
Add a second template so the Go output is untouched:

```yaml
# buf.gen.rust.yaml, at the repository root: buf generate --template buf.gen.rust.yaml
version: v2
inputs:
  - directory: proto
    paths:
      - proto/skein
plugins:
  - local: protoc-gen-prost
    out: rust/crates/proto/src/gen
    opt:
      - bytes=.
      - compile_well_known_types
      - extern_path=.google.protobuf=::pbjson_types
      - file_descriptor_set
  - local: protoc-gen-prost-serde
    out: rust/crates/proto/src/gen
  - local: protoc-gen-tonic
    out: rust/crates/proto/src/gen
    opt:
      - compile_well_known_types
      - extern_path=.google.protobuf=::pbjson_types
  - local: protoc-gen-prost-crate
    out: rust/crates/proto
    strategy: all
    opt:
      - gen_crate=Cargo.toml
```

Install the plugins with `cargo install protoc-gen-prost
protoc-gen-prost-serde protoc-gen-tonic protoc-gen-prost-crate` at pinned
versions, and record the versions in the template's header comment as
`buf.gen.yaml` does. The option values above are the ones the plugins'
README shows; check each plugin's own README for the version you install.

`bytes=.` makes every `bytes` field a `bytes::Bytes` (cheap clones for CRDT
batches and event payloads). `file_descriptor_set` embeds the descriptors,
which the gateway's route table and gRPC reflection need.
`extern_path=.google.protobuf=::pbjson_types` makes `Timestamp` and
`Duration` serialise as ProtoJSON strings.

Before you commit to this route, check that the `protoc-gen-tonic` release
generates code for the tonic version in the workspace. If it lags, use B.

### B. `build.rs` from a buf-built descriptor set

```
buf build proto --path proto/skein -o rust/crates/proto/skein.binpb   # commit it, or run in a make target
```

```rust
// rust/crates/proto/build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let descriptor_bytes = std::fs::read("skein.binpb")?;
    let descriptors = prost::Message::decode(descriptor_bytes.as_slice())?;
    tonic_prost_build::configure()
        .bytes(["."])
        .compile_well_known_types(true)
        .extern_path(".google.protobuf", "::pbjson_types")
        .file_descriptor_set_path(std::env::var("OUT_DIR")? + "/skein.binpb")
        .compile_fds(descriptors)?;
    pbjson_build::Builder::new()
        .register_descriptors(&descriptor_bytes)?
        .build(&[".skein.v1"])?;
    Ok(())
}
```

`buf` still owns parsing, imports and lint, so the Rust code sees exactly
the descriptors the Go code was generated from; no `protoc` is needed at
build time. The cost is that generated code is not committed and not
reviewable in pull requests.

### The crate

```
rust/crates/proto/
  Cargo.toml        prost, prost-types or pbjson-types, pbjson, serde, bytes; tonic behind a feature
  src/lib.rs        pub mod skein { pub mod v1 { include!(...) } }, pub const FILE_DESCRIPTOR_SET
```

Put tonic behind a `grpc` feature (on by default). The service `-core`
crates use the messages with `default-features = false`, so domain and app
code never depends on the transport (see the design doc's crate rules).

## Port order

1. Generate messages only (`protoc-gen-prost`), build the crate, and write
   one round-trip test: encode every message type's default value and a
   populated example in Rust, decode it with Go (a scratch test in
   `gen/go`), and the reverse. Compare decoded messages, not bytes: both
   encoders are deterministic for the same schema, but map fields are
   allowed to differ in order.
2. Add pbjson. Prove it with the JSON examples in `docs/api/*.md`: each
   block tagged ```` ```json skein.v1.<Message> ```` must parse into that
   message and serialise back to an equal value. `contracttest`'s
   `TestDocExamplesMatchTheirMessages` checks the same examples in Go; a Rust
   test over the same files keeps the two in step.
3. Add tonic stubs. Prove them with a Rust client calling a Go service (for
   example identity's health check and `GetUser` on the native stack), and
   a Go client (`grpcurl` is enough) calling a Rust server.
4. Expose `FILE_DESCRIPTOR_SET` and read the `google.api.http` rules with
   `prost-reflect`. Prove it by building the route table and comparing it
   with the routes the Go gateway's `LoadRoutes` builds (the list in
   `docs/api/README.md` is the same data).

## What does not get ported

- `gen/go/contracttest` stays in Go: it checks the protos, the OpenAPI
  document and the docs against each other, and none of those change in the
  port.
- `gen/openapi/skein.swagger.json` keeps coming from `protoc-gen-openapiv2`.
  The Rust gateway serves the same file with `include_str!`.
- `gen/python` stays for `ml` and `agent` as long as they are in Python.

## Pitfalls

- **Enums are `i32` in prost.** A message field holds the raw number; use
  `Role::try_from(field)` and treat unknown values as errors, as the Go code
  does with `.Valid()` checks.
- **`oneof` is an `Option<enum>`.** `Event.payload` becomes
  `Option<event::Payload>`; a missing payload is `None`, which Go code
  reports as an invalid event.
- **Field presence.** proto3 scalars without `optional` have no presence; an
  empty string and a missing string are the same. The Go code already
  relies on this; do not add `Option` where the proto has none.
- **JSON 64-bit integers are strings**, enum values are names, and default
  values are omitted. `pbjson` does all three; plain `serde` derives on
  prost types do none of them.
- **Package naming.** prost turns `skein.v1` into `skein::v1`; Go code calls
  it `skeinv1`. Re-export it as `skein_proto::v1` to keep call sites short.
- **Comments.** The agent reads RPC comments from the descriptor set to
  describe its tools; keep source info in any descriptor set you generate
  (`buf build` keeps it by default, `--exclude-source-info` drops it).
