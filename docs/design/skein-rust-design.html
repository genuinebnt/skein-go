Skein

A collaborative notes engine: a Rust document engine with its own CRDT, diff and history, plus the ML algorithms that make a pile of notes searchable and self-organizing.

Summary

People edit rich-text documents together in real time, and offline edits merge without conflicts. On top of that, the system finds notes by typo-tolerant text search and by meaning, groups notes into topics, and links related notes into a graph. An agent works with the notes as a collaborator: it researches across them, answers with citations, and proposes edits you can accept or reject.

The project has one purpose: learn Rust, algorithms and ML by building real components from scratch, then measuring them against reference implementations.

Scope and phases

Phase 1, nownow Document engine, ML algorithms and the agent. One Cargo workspace, one small Axum binary for demos. No auth beyond a dev token, no separate services.

Phase 2, laterlater Split into services on GCP: gateway, auth, notification, sync, search. The Phase 1 crates become the libraries those services call, so nothing is rewritten.

Phase 3, after thatphase 3 Scale, advanced ML, offline-first clients and operations. Starts only when Phase 2 is deployed and measured, because it needs real traffic data to aim at.

Goals

  • Converging real-time editing with rich-text formatting, backed by a CRDT written in this repo.
  • Document diff, change history with time travel, and per-user undo and redo.
  • Trigram search, semantic search with an ANN index, hybrid ranking, clustering and a backlink graph.
  • An agent runtime built from scratch that answers questions over the notes with citations and proposes edits as a suggestion, never as a silent change.
  • Every algorithm verified against a reference and benchmarked.

Non-goals for Phase 1

  • Production auth, billing, multi-tenant isolation or a polished UI. Use ProseMirror or Tiptap for the editor surface.
  • Training embedding models or language models. Use an existing small embedding model through Candle or ONNX, and reach the language model through a trait (hosted API or local).
  • Beating Automerge or FAISS. Aim to understand the gap, then close part of it.

Document engine now

Sequence CRDT

Start with RGA to learn the model, then move to a Fugue-style algorithm that avoids interleaving anomalies. Store runs of characters inserted together as one item, and use a B-tree or skip list so position lookups stay logarithmic. Replicas exchange version vectors and send only missing operations.

Rich text

  • Formatting marks (bold, italic, link) are spans anchored to characters, with merge rules from the Peritext paper.
  • Blocks (paragraph, heading, list) form a tree. Moving a block must never create a cycle.
  • The binary update format uses varints and run-length encoding. Its decoder rejects malformed input and is fuzzed.

Markdown

A hand-written block and inline parser turns Markdown into the document model, and a serializer turns it back. Parse then serialize must round-trip on generated input. Typing # or **text** uses the same rules as input shortcuts.

Go changed thisGo changed this Fugue was implemented directly (ADR-0005), with one operation per character in wire format v1 (no runs yet) and a node arena rather than a B-tree. Blocks are not a tree: they are block markers inside the one sequence, with last-writer-wins attribute registers (type, indent, checked, language), so there are no block moves and no cycles to prevent. Inline formatting is Markdown inside the block text rather than Peritext marks. The normative formats are docs/spec/crdt-sequence.md and docs/spec/blocks.md.

Diff, change history, undo and redo now

FeatureDesign

Change historyAppend-only op log with a snapshot every N operations. Time travel replays from the nearest snapshot to any version. Each operation carries its author, so blame works per character.
CompactionOld operations fold into snapshots, tombstones are garbage collected once every known replica has seen the delete.
Undo and redoEach user has their own stack of inverse operations, so undo reverses only your changes even after others edited nearby. Related edits typed within a short window group into one undo step.

Agent now

The agent is a collaborator that can read the whole workspace. It answers questions with citations to specific blocks, researches a topic across clusters, summarizes, and suggests edits, links and tags. The runtime is written in this repo so the loop, the tools and the evals are all understood end to end.

Runtime

  • Tool trait: each tool has a name, a JSON schema for its arguments and an async call that returns structured output or a typed error.
  • Loop: plan, call tools, observe, repeat until done. Hard limits on steps, tokens and wall time. Cancellation propagates to running tools.
  • Model backend trait: one implementation for a hosted API and one for a local model, so the loop never depends on a vendor.
  • Tool-call parser: reads the model's output, repairs malformed JSON where it safely can, and returns errors the model can act on.
  • Concurrency: independent tool calls run in parallel on Tokio tasks, each with a timeout.
  • Traces: every run stores its prompts, tool calls and results so any run can be replayed and debugged.

Editing safely

  • The agent is a CRDT peer with its own identity and cursor. Its edits are held as pending operations until a person accepts them, and can be rejected as a group.
  • It has the same permissions as the user who invoked it, and it cannot delete notes.
  • Text inside notes is data, never instructions. A note that says "ignore previous instructions" must not change the agent's behavior.

Evaluation

  • A fixed task set over a sample workspace: factual questions, multi-hop questions, summaries and edit requests.
  • Metrics: task success, citation faithfulness (does the cited block support the claim), tool-call correctness, steps used, latency and cost per task.
  • Traces make regressions replayable: re-run the same task after a change and compare.

An optional extension: choose the cheapest set of tool calls under a budget with a knapsack-style DP.

Go changed thisGo changed this The agent was built in Python on LangGraph (ADR-0015), not as a from-scratch runtime. It acts as its user with a delegated token, through the same gRPC APIs as the frontend (ADR-0009). It may delete notes and share them, but only after the user confirms each such call. Edits are applied at once as one ApplyOps batch, which is one undo group, so a suggestion is rejected by undoing it rather than held as pending operations. Writing the runtime from scratch in Rust remains the optional last step of the port (services/agent/PORTING.md).

Porting from Go now

The Rust version is now a port of the Go code, one crate per Go module or package, in one Cargo workspace in rust/ at the root of the skein-go repository. The protos, conformance fixtures, seed data and end-to-end suite are then shared by path, and a Rust service can replace its Go twin in the running stack while everything else stays in Go. The porting guides are in docs/porting/: the entry point with the dependency graph, the order and the side-by-side setup; a PORTING.md next to every library, platform/, gen/ and every service; and seven vertical slices that port one feature at a time, from route to storage.

Order and acceptance

  1. Libraries, against testdata/conformance/ and the codec golden bytes.
  2. skein-proto, generated with buf and the prost and tonic plugins (gen/PORTING.md).
  3. Platform, in dependency order, porting each package's fake with it.
  4. Services: identity, documents, search, notifications, then the gateway; the agent last and optional; ml stays in Python.

A ported service is done when its Go unit tests pass in Rust under the same names, its seed loader matches the seed's ground truth, and the end-to-end suite (make e2e) passes with that service in Rust and the rest in Go: same protos, same ports, same environment variables, same database migrations.

Testing and benchmarks

  • Convergence: random concurrent operations on N replicas with random delivery order must end identical. Seeded and replayable.
  • Round trips: parse then serialize, encode then decode, diff then apply.
  • Fuzzing: the binary decoder and the Markdown parser.
  • Concurrency: loom for atomics, miri for unsafe code.
  • Performance: criterion with fixed seeds, flamegraphs, and a PERF.md log with a hypothesis and measured result for every optimization.
  • Agent: scripted fake model backend for deterministic loop tests, recorded traces for replay, and the eval task set for quality.
  • Datasets: the public editing traces for CRDT speed, SIFT1M and GloVe for ANN, and your own notes for search quality.

Risks and open questions

  • Block moves in the tree CRDT are hard to get right. Fallback: delete and reinsert, accepting duplicate-move anomalies at first.
  • HNSW deletes and updates suit a constantly changing editor poorly. Plan: tombstones plus periodic rebuild.
  • Incremental clustering drift: mini-batch centroids degrade over time. Schedule a full re-run and track inertia.
  • Agent reliability: models produce malformed tool calls and unsupported claims. Mitigation: strict schemas, repair and retry limits, citation checks in the evals, and suggestion-only edits.
  • Encryption versus features: end-to-end encryption would stop the server from indexing text or running the agent on it. Decide during Phase 2 whether it is in scope, because it changes the architecture.
  • Scope: this is a large list. Ship M1 to M3 before starting search, and treat labs as bounded time boxes.
  • Open: Fugue or a simpler algorithm first? Which embedding model balances size and quality on a laptop CPU?
